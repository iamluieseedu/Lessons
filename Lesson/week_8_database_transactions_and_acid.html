The GCash / Bank Transfer Scenario
Real-World Problem
The Action: Transferring ₱2,000 from Juan to Maria

To move money between accounts, the database must execute two separate SQL commands:

Standard SQL Execution⚠️ DANGEROUS WITHOUT TRANSACTIONS
-- Step 1: Deduct ₱2,000 from Juan's account (SUCCEEDS!) UPDATE accounts SET balance = balance - 2000 WHERE id = 101; -- ⚡ [CRITICAL OUTAGE]: Server loses power or internet disconnects right here! -- Step 2: Add ₱2,000 to Maria's account (NEVER RUNS!) UPDATE accounts SET balance = balance + 2000 WHERE id = 202;
What just happened? Juan lost ₱2,000, but Maria never received it. The ₱2,000 vanished into thin air! Without transactions, databases are vulnerable to permanent financial corruption.
What is a Transaction?

A transaction bundles multiple SQL statements into a single indivisible logical unit of work (LUW).

The Golden Guarantee

Either EVERY step completes successfully, or the entire operation is automatically cancelled and restored (ROLLBACK) as if nothing happened.

No half-done updates. No lost money. No corrupted records.

Architecture Overview
A — Atomicity: The "All or Nothing" Rule
A transaction cannot be chopped into half-finished pieces
Pillar 1
How Atomicity Works in SQL

When you start a transaction, the database buffers your changes. It only makes them permanent if you reach the very end without an error.

Syntax BlueprintTRANSACTION CONTROL
START TRANSACTION; UPDATE accounts SET balance = balance - 2000 WHERE id = 101; UPDATE accounts SET balance = balance + 2000 WHERE id = 202; -- If ALL statements succeed: COMMIT; -- If ANY error, crash, or constraint violation happens: ROLLBACK;
  • COMMIT: Permanently saves all changes to disk.
  • ROLLBACK: Completely discards all changes and reverts the database to its exact initial state.
The Vending Machine Mental Model

Imagine buying chips from a vending machine:

1. You insert ₱50: The machine holds your coin in the escrow buffer.
2. Coil turns: The snack drops through the beam sensor.
3. Success (COMMIT): The sensor detects the bag, drops your coin into the vault, and completes the sale.
4. Jammed (ROLLBACK): If the snack gets stuck, the machine immediately refunds your ₱50!
The machine NEVER keeps your money while leaving you empty-handed. That is pure Atomicity!
C — Consistency: Preserving Database Rules
Transactions can only take the DB from one valid state to another
Pillar 2
What is Consistency?

A database contains integrity rules: Primary Keys, Foreign Keys, and CHECK Constraints. A transaction is forbidden from violating any rule.

  • No Negative Balances: CHECK (balance >= 0) prevents anyone from withdrawing more than they own.
  • Conservation of Money: The total funds in the banking system must stay identical before and after any transfer.
  • Orphan Prevention: Foreign keys ensure you cannot create an order item for a product ID that doesn't exist.
If an update attempts to set a balance to -₱500, the DBMS halts the query instantly and forces an automatic rollback.
Before & After State Invariant
Account Before Transfer After Transfer
Juan (101) ₱10,000 ₱8,000
Maria (202) ₱3,000 ₱5,000
Total Funds ₱13,000 ₱13,000 (Preserved!)

Rule Enforced: Total money in the system is conserved. Zero phantom money was created or lost.

I — Isolation: Handling Concurrent Users
Shopee Flash Sales & Concert Ticket Booking Race Conditions
Pillar 3
The Concurrency Nightmare (Race Conditions)

Imagine there is only 1 iPhone remaining in stock during a 12:00 midnight Flash Sale. Two buyers (User A and User B) click "Place Order" at the exact same millisecond!

Without Isolation:

Both see stock = 1 $\to$ both orders succeed $\to$ stock drops to -1! Two customers paid, but the company only has 1 phone!

With Isolation (Row Locks):

User A's transaction locks the row. User B waits in line until A commits. Then B is told: "Out of Stock".

Pessimistic Locking in SQL
-- Locks the stock row so no one else can read or touch it until we COMMIT! SELECT stock_qty FROM products WHERE id = 99 FOR UPDATE;
What is a "Dirty Read"?

A Dirty Read happens when User B reads uncommitted changes made by User A.

1. Juan transfers ₱5,000 to Maria.
2. Maria's screen immediately shows ₱5,000.
3. Juan's transaction errors out and ROLS BACK.
4. Maria tries to spend money that was never truly committed!

Isolation prevents this: Other users only see committed data.

D — Durability: Surviving Power Cuts & Reboots
Once Committed, Data is Written to Non-Volatile Disk Forever
Pillar 4
What is Durability?

Once you receive the message "Transaction Committed Successfully", the changes are permanent. Even if an earthquake unplugged the database server 1 millisecond later, the data is completely safe.

  • RAM is Volatile: Data stored only in memory disappears the instant electricity drops.
  • Write-Ahead Logging (WAL): Before writing to the complex database tables, the engine appends the transaction changes to an ultra-fast, append-only disk log file.
  • Crash Recovery: When the server reboots:
    • REDO Phase: Replays all committed transactions from the WAL log.
    • UNDO Phase: Erases any incomplete, uncommitted transactions.
The 2-Tier Storage Flow
RAM (Volatile Memory)

Blazing fast, but wipes clean during power failure.

Flush to Disk on COMMIT
NVMe SSD / Disk (Non-Volatile)

Guaranteed to survive crashes, reboots, and power cuts.

What is a SAVEPOINT?

Normally, a ROLLBACK wipes out everything in the transaction. A SAVEPOINT creates a checkpoint in the middle of your work so you can roll back only the flawed step.

SQL Syntax
START TRANSACTION; INSERT INTO cart VALUES ('Keyboard', 1200); SAVEPOINT after_keyboard; -- User adds invalid item (e.g. out-of-stock GPU) INSERT INTO cart VALUES ('RTX 4090', 95000); -- Roll back ONLY to savepoint! Keeps the Keyboard! ROLLBACK TO after_keyboard; COMMIT;

How Backend Developers Use Transactions
Production Code in PHP (Laravel/PDO) and Node.js
Production Code
PHP / PDO Pattern (try ... catch)
<?php try { $pdo->beginTransaction(); $stmt1 = $pdo->prepare("UPDATE accounts SET balance = balance - ? WHERE id = ?"); $stmt1->execute([2000, 101]); $stmt2 = $pdo->prepare("UPDATE accounts SET balance = balance + ? WHERE id = ?"); $stmt2->execute([2000, 202]); // Both succeeded! Make it permanent: $pdo->commit(); } catch (Exception $e) { // If ANY error occurred, undo everything! $pdo->rollBack(); }
Node.js / PostgreSQL Pattern
const client = await pool.connect(); try { await client.query('BEGIN'); await client.query( 'UPDATE accounts SET balance = balance - $1 WHERE id = $2', [2000, 101] ); await client.query( 'UPDATE accounts SET balance = balance + $1 WHERE id = $2', [2000, 202] ); await client.query('COMMIT'); } catch (err) { await client.query('ROLLBACK'); } finally { client.release(); }

Quick Reference & Key Takeaways
The 4 Golden Rules of Database Reliability
Summary
Atomicity (A)

All or Nothing. If even 1 statement fails out of 10, the database rolls back to 0. No partial updates.

Consistency (C)

No Broken Rules. Constraints, foreign keys, and non-negative balances are strictly preserved.

Isolation (I)

No Cross-Interference. Concurrent users cannot read uncommitted (dirty) data from other users.

Durability (D)

Disk Permanence. Committed data survives power loss and hardware crashes via Write-Ahead Logs.
